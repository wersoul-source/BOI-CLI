# RCA — v2.6.1 runtime hardening

Scope: the path Provider → Capability Probe → Tool Dispatcher → Observation →
Task Completion, plus streaming and terminal rendering.

Evidence rule used here: a finding is **Confirmed** only when a file and line
prove it, or a test reproduces it. Anything else is marked **Hypothesis** and
says what would settle it. The reported run used `maxplus/deepseek-v4.1-flash`,
whose endpoint this sandbox cannot reach, so nothing below rests on a live call
to that provider.

---

## F-1 Native tool calling is gated behind a text-envelope probe — Confirmed

`internal/core/qualification.go:148`

```go
env.ToolCalling = env.Completion && profile.Allows("tool_calling") && profile.Allows("tool_observation") && profile.Allows("authority")
env.NativeTools = env.ToolCalling && profile.Allows("native_tool_schema")
```

`tool_calling` is measured only by `probeEnvelope`
(`qualification.go:196`), which demands the model emit BOI's own
`<boi-action>{…}</boi-action>` JSON envelope. `native_tool_schema` is measured
separately and correctly: it sends real `tools` over the Chat Completions
protocol and checks that the model calls `workspace__read` with
`{"path":"README.md"}` (`qualification.go:328`).

The two measure different protocols, but the native result is multiplied by the
envelope result. The reported profile is exactly the case that breaks:
`native_tool_schema passed`, `tool_calling failed — envelope JSON does not
decode`. A model that demonstrably performs native tool calls is therefore
denied **all** tool access.

Downstream the denial is total, not partial:

- `Broker.CapabilityNames()` returns `nil` when `toolCallingAllowed` is false
  (`broker.go:185`), so every Tool reads *registered, not offered*.
- `Broker.NativeTools()` returns `nil` on the same flag (`broker.go:350`).

**Impact:** the product's main feature is off for any model that will not speak
BOI's bespoke envelope, regardless of whether it speaks the industry-standard
one.

## F-2 Probe failures are not diagnosable — Confirmed

`qualification.go:217` and `:189` report `"envelope JSON does not decode"` and
`"expected %q not found"` without any excerpt of what the model actually
replied. `runProbe` discards `response.Content` after `probe.check` runs
(`qualification.go:320`).

**Impact:** `boi provider qualify` states a verdict that cannot be acted on. The
two failures in the reported run cannot be explained from the output alone —
which is why this RCA cannot yet state *why* that model's JSON failed to decode.

## F-3 Probe output budget is 256 tokens — Hypothesis

`qualification.go:310` sends `MaxTokens: 256` for every probe. A model that
emits a reasoning preamble before its answer can be cut off mid-JSON, which
decodes as a failure rather than as truncation.

Not confirmed: truncation would usually also drop the closing `</boi-action>`
tag and trip the earlier "expected exactly one envelope" branch instead.
Settled by F-2's excerpt plus recording `finish_reason`, which the adapter does
not currently read (`openai.go:81`).

## F-4 A task that needed tools reports `completed` — Confirmed

`engine.go:372`

```go
unevidenced := effects == 0 && (toolCalls == 0 || attempts > 0 || hasCodeFence(decision.Response)) && e.ungrounded(task, decision.Response)
```

`e.ungrounded` is supplied in `service.go:417`:

```go
Ungrounded: func(task, response string) bool {
    return interactive && s.broker.CanChange() && namesWorkspaceFile(...)
}
```

`Broker.CanChange()` iterates `CapabilityNames()`, which is `nil` whenever tool
calling is disabled (`broker.go:185`, `:324`). So the grounding challenge is
switched **off precisely when no tool exists to do the work** — the one case it
was written for. `DecisionRespond` then falls through to `StopCompleted`
(`engine.go:397`) and `outcomeFor(0,0,0)` returns `OutcomeAnswered`
(`effects.go:74`). No notice, no blocked status.

Second defect in the same check: `namesWorkspaceFile` (`grounding.go:15`) only
matches tokens for which `exists(token)` is true — a file **already present**.
A task whose whole point is to *create* `agent-trial-001/` or `report.json`
names nothing that exists yet, so it is never challenged even when tools are
available.

**Impact:** both reported behaviours — the agent narrating work it never did,
and the run being recorded as a clean completion — follow from this. There is
no `BLOCKED` outcome in the vocabulary at all (`effects.go:65`).

## F-5 There is no streaming anywhere — Confirmed

Three independent facts:

1. `OpenAIProvider.Stream` (`openai.go:210`) calls `Complete`, waits for the
   whole body, then pushes the entire text as a single token. It is a stub with
   a streaming signature.
2. `openAIRequest.Stream` is hard-coded `false` (`openai.go:102`); no SSE
   parser exists in the adapter.
3. `Provider.Stream` has no caller in the runtime. The only call site in the
   repository is `adapters_test.go:206`. The agent loop uses
   `router.Complete` (`service.go:344`).

**Impact:** the acceptance criterion "text appears while the model answers"
cannot hold today at any layer: HTTP, adapter, runtime, or TUI.

## F-6 Chat bubbles are never wrapped — Confirmed by test

`chat.go:131`

```go
for _, line := range lines {
    sb.WriteString(style.vert + " " + line)
    pad := boxW - term.ThaiStringWidth(line) - 1
```

`boxW` is clamped to the terminal (`chat.go:108`) but the **line is not**. A
long paragraph is emitted at full length and the terminal hard-wraps it, so the
right border lands in the middle of the next row.

Reproduced: at terminal width 60 a 300-character Thai line renders a 303-column
row. `pad` goes negative and is clamped to 0, putting the border flush against
the text. This is the shattered-frame symptom in the reported screenshots.

## F-7 Width is miscounted for emoji and most non-Latin scripts — Confirmed by test

`terminal/console.go:80`

```go
func isWideRune(r rune) bool {
    return unicode.Is(unicode.Han, r) || unicode.Is(unicode.Hangul, r) ||
        r >= 0xFF01 && r <= 0xFF60 || r >= 0xFFE0 && r <= 0xFFE6
}
```

Measured: `🙏`, `📋`, `✅` all return width 1; terminals render them as 2. Also
missing: Hiragana/Katakana, CJK punctuation (U+3000–303F), variation selector
U+FE0F, ZWJ sequences, regional indicators. Zero-width handling covers Thai only
(`console.go:34`) — Devanagari, Arabic and Hebrew combining marks still count 1.

**Impact:** every emoji in a bubble shifts that row's border one column left.

## F-8 Resize does not reflow — Confirmed

`ChatModel.SetSize` (`chat.go:171`) updates `width`, `height` and the viewport
but never calls `renderMessages()`. `renderMessages` runs only from
`AddMessage`/`AddAgentMessage` (`chat.go:37`, `:51`). On `tea.WindowSizeMsg`
(`app.go:226`) the already-rendered boxes keep their old geometry; the viewport
then truncates them horizontally, cutting the right border away.

## F-9 Rendering panics before the first WindowSizeMsg — Confirmed by test

With `c.width == 0`, `chat.go:108` sets `boxW = -6` and `chat.go:128` calls
`strings.Repeat(" ", -6)`.

Reproduced: `panic: strings: negative Repeat count`.

## F-10 The workspace is a single immutable root with no grant policy — Confirmed

`workspace.Sandbox` (`sandbox.go:15`) holds one `root` fixed at construction.
Every resolve is `within(root, candidate)` or an error (`sandbox.go:106`). There
is no second root, no allow-list, no scoped or one-time grant, and no API to add
one.

**Impact:** requirement 4 (several folders, per-occasion permission, without
disabling the sandbox) is unimplemented rather than broken. It needs design, not
a fix.

## F-11 The `maxplus` catalog entry omits the API version segment — Confirmed

`catalog/providers.json:284` is `https://api.maxplus-ai.cc`, while the
provider documents `/v1/chat/completions` and `/v1/models`. The adapter appends
`/chat/completions` (`openai.go:110`) and the wizard appends `/models`
(`setup/models.go:19`), producing unversioned URLs. Every other OpenAI-style
entry in the catalog carries its version segment.

Introduced by commit `a373b29` (this branch). The reported run predates it and
used a hand-configured `.env`, which is why the probes reached the model at all.

## What the reported session actually was

F-1 denied every Tool. With no tools offered, the model fell back on the
tool-call syntax from its own training and emitted it as plain prose — visible
in the screenshots as raw `invoke name="bash"` markup, which BOI does not parse
and the TUI simply printed. F-4 then let the run finish as `completed`. F-6 to
F-8 broke the frames around that output.

None of it required a bug in the Maxplus integration itself.
